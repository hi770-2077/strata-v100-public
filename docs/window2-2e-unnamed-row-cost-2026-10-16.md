## 1. 事情的起点：先找"剖析器关掉了什么"

想给那笔隐形开销称重，第一步是弄清楚 `prof_on_` 到底动了什么。答案是五个开关，但**其中三个是假的**：

| 位置 | 被剖析器关掉 | 实际情况 |
|---|---|---|
| 1634 / 1662 / 1677 | `fuse_wait` / `fuse_rows` / `hits_in_combine` | **HIP-only**（CUDA 构建直接 `return false`）⇒ 与我们无关 |
| 1161 | `fuse_ab`（conv + a/b 融合） | **HIP-only**（CUDA `return false`）⇒ 与我们无关 |
| 906 | `br`（df_branch 侧支） | `STRATA_DF_BRANCH` 默认关闭 ⇒ 本来就关着 |
| **1459 / 1684** | **`sh_fork`：共享专家跑独立流** | **CUDA 默认开启**（218 行 `return true`）⇒ 唯一真实差异 |

也就是说，剖析器真正改变的只有一件事：**把共享专家从旁路流拽回主流**。它是本轮唯一能 A/B 的变量。

## 2. 共享专家旁路流：净赚 +1.7~2.2%（保留开启）

`STRATA_SH_STREAM=0` vs 默认，确定性配对（3 轮 × 4 条 min_p/prompt）：

| | min_p=1.0（T=1 窗） | min_p=0.0（T=4 窗） |
|---|---|---|
| 默认（旁路流开） | 86.70 tok/s | 104.65 tok/s |
| `STRATA_SH_STREAM=0` | 85.20 | 102.30 |
| | **−1.73%** | **−2.25%** |

**结论一：这个 fork 在我们这张卡上是赚的。** 源码注释说 HIP 上跨流 event 依赖比共享专家本身还贵
（同一二进制 62.9 vs 43.4 tok/s），我们在 PCIe 双卡上不是这种情况——别照搬别人的结论，测了才算。

**结论二：它解释不了那笔隐形开销。** 折算成窗口只有 **0.086 + 0.124×T ms**，
而待解释的量级是 ms/行级别。差一个数量级。

## 3. 三种比法，只有一种是对的

盯着屏幕上一堆数字很容易比错。把三种比法摆在一起才看清：

| 比法 | 结果 | 是否可用 |
|---|---|---|
| 相位**和**斜率 3.09 vs 剖析器关的墙钟斜率 4.68 | 差 1.59 ms/行 | ❌ **单位不同**：一个是双卡 stage 相加，一个是并行后的墙钟。且两卡重叠率随 T 变（实测 T=1 因子 1.59、T=4 因子 1.07），没有固定换算率 |
| 剖析器开 7.76+4.99T vs 剖析器关 7.16+4.50T | 差 0.60 固定 + 0.49 ms/行 | ✅ 同单位 —— 但这是**剖析器自身的代价**（打点开销 + 关掉 fork），不是生产中存在的开销 |
| **剖析器开的墙钟斜率 4.99 vs 相位斜率 3.09** | **差 1.90 ms/行** | ⚠️ 这才是"未打点的工作"，但分母（相位）本身是坏的，见下节 |

（第一行的错就是 2-2c §4「~1.90 ms/行」的来源 —— 数字碰巧接近，推导是不成立的。）

## 4. 真正的发现：T≥2 时半个窗口没上秤

```
verify.cpp:877   const int G = (split_ && T >= 2 && !batch_rec_) ? 2 : 1;
verify.cpp:2434  if (prof_on_ && G == 1) collect_profile();
verify.cpp:1106  (prof_on_ && grp == 0) ? prof_ : nullptr
```

三条串起来：**T≥2 的窗口被拆成两个 group，而只有 group 0 打点、只有 G==1 的窗口收集。**

- 2-2c 的 **T=1 列 = 全部工作**（G=1）；
- 2-2c 的 **T=4 列 = group 0，约占一半**；
- 于是 `(T=4 列 − T=1 列) / ΔT` 是拿**全部**减**一半** ⇒ 每个 ms/行都被低估。

粗略校对：**一批小相位几乎不随 T 变**（`gate` 0.10→0.10、`copy+combine` 0.30→0.30、
`attention` 0.46→0.43、`rec` 0.42→0.63），而随 T 涨的相位（VRAM hits 3.06→7.05）涨幅约 2.3× ——
与「T=4 时每个 group 装 2 行」的量级一致，也印证了「另一半没进来」。

## 5. 顺手拿到的干净数（与坏表无关）

剖析器关、只留 `STRATA_DECODE_TIMING`，当前二进制（含 ②-2d 的 Q8_0 交错）：

```
T=1.00: 11.66 ms/窗, 1.00 token/窗
T=3.98: 25.08 ms/窗, 2.70 token/窗
拟合: ms/窗 = 7.16 + 4.50*T   (2-2c 是 6.98 + 4.68T: 固定 +2.6%, 每行 -3.8%)
```

引擎**直接报 token/窗**，不需要我们反推接受率：T=3.98 时 2.70 token ⇒ 三个草稿位平均接受率 **0.567**。
而加一个草稿行的**收支平衡接受率 = 4.50 / 9.29 = 0.484**（9.29 = 25.08/2.70 ms/token）。
⇒ 0.567 > 0.484，**第四个草稿行仍然微赚**，生产 T≈2.2 这个工作点是合理的、但不是激进的；
这也解释了为什么引擎会把验证窗宽自动扩到 4~8。

**注意 ②-2d 的改动把每行成本压低了 3.8%**（6.98+4.68T → 7.16+4.50T）—— lm_head 那 644 MiB 每窗硬读
变便宜了，与设计预期一致；固定项反而 +2.6%，说明这次优化收益集中在多行窗口上（与端到端
「T=1 只 +0.2%、T=4 +2.1%」完全吻合）。

## 6. 下一步（按正确性排，不是按收益排）

1. **先修秤，再称重。** 把相位收集覆盖两个 group（`gpu_stamp` 不再只对 `grp==0`、`collect_profile`
   不再要求 `G==1`），或直接用 **nsys 抓单个验证窗**拿到权威的逐内核墙钟。
   **在这个动作完成之前，不要再引用 2-2c 的任何「ms/行」数字做决策。**
2. 秤修好后重测「专家读」的有效带宽 —— 它决定候选①（跨行共享）是否复活。
   注意：源码显示 GpuPlanSink 已按 distinct expert 去重，**跨窗重复读并不存在**；
   所以即便带宽只有 41%，要解的问题也不是"去重"，而是**单次访问的效率**（占用率/展开/扇区）。
3. 其余候选排序不变：`fuse_*` 三个融合在 CUDA 上不存在；HC 量化两档判死；草稿深度在平衡点上。
