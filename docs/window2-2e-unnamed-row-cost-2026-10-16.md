## 1. 起点：剖析器到底关掉了什么

`prof_on_` 动了五个开关，但**其中四个对我们根本不存在**：

| 位置 | 开关 | 实际情况 |
|---|---|---|
| 1634 / 1662 / 1677 | `fuse_wait` / `fuse_rows` / `hits_in_combine` | **HIP-only**：CUDA 构建直接 `return false` |
| 1161 | `fuse_convab` | **HIP-only**：CUDA 直接 `return false` |
| 906 | `br`（df_branch 侧支） | `STRATA_DF_BRANCH` **默认就关着** |
| **1459 / 1684** | **`sh_fork`：共享专家跑独立流** | **CUDA 默认开启**（218 行 `return true`）⇒ 唯一真实差异 |

⇒ 剖析器真正改变的只有一件事：把共享专家从旁路流拽回主流。它也是唯一能做 A/B 的变量。

## 2. 确定的结论：共享专家旁路流是净赚的（保留开启）

`STRATA_SH_STREAM=0` vs 默认，确定性配对（3 轮 × 4 条 min_p/prompt，不加 nonce）：

| | min_p=1.0（T=1 窗） | min_p=0.0（T=4 窗） |
|---|---|---|
| 默认（旁路流开） | 86.70 tok/s | 104.65 tok/s |
| `STRATA_SH_STREAM=0` | 85.20 | 102.30 |
| | **−1.73%** | **−2.25%** |

**别照搬别人的失败结论。** 源码注释写得很具体：HIP 上一个跨流 event 依赖比共享专家本身还贵
（同一二进制、同一 48,067-token prompt，R9700 上 62.9 vs 43.4 tok/s）。**我们在 PCIe 双卡上不是这种情况。**

顺带一个机制意义：它也跑在旁路流上，所以**剖析器的时间戳天然罩不住它** —— 这解释了为什么
「剖析器 vs 生产」的差值里有一部分是它（实测只值 0.086 + 0.124×T ms，量级很小）。

## 3. 我测错的那个假设（留作教训）

从 §2 出发想找更大的隐形项，读到三行代码：

```
verify.cpp:877   const int G = (split_ && T >= 2 && !batch_rec_) ? 2 : 1;
verify.cpp:2434  if (prof_on_ && G == 1) collect_profile();
verify.cpp:1106  (prof_on_ && grp == 0) ? prof_ : nullptr
```

看起来无懈可击：T≥2 拆两个 group，而只收 group 0 ⇒ 每行 ms 系统性偏低约一倍。
据此写了补丁（缓冲区按 group 分片、`gpu_stamp` 覆盖所有 group、`accumulate_profile` 求和、
`collect_profile` 不再要求 `G==1`），重建、重跑。

**结果：数字一动不动。** 于是加了一行诊断，直接对每个 group、每个窗口打印是否打点 ——

```
strata verify profile: window 0 group 0 stamped ...
strata verify profile: window 1 group 0 stamped ...     ← 连 T=3.94 的窗口也只有 group 0
```

**⇒ 我们这套配置下 `split_` 为假、G 恒等于 1，整个假设的前提不成立。**

补丁本身没错（`split_` 一旦为真，上游那段代码确实是错的），已作为**潜在 bug 修复**保留在 fork 里，
在当前配置下是安全的空操作。**但由此推出的「2-2c 的表少了一半」必须撤回。**

## 4. 那 2-2c 的表到底还能不能用

能用和不能用要分开说：

- **不能用**：任何**绝对值**的墙钟换算。「两 stage 相加」与「并行后的墙钟」不是一个单位，
  而且换算率本身随 T 变 —— 实测 T=1 时 相位和/墙钟 = 1.59，T=4 时 = 1.09
  （T=1 时两张卡更多时间在互相等，相加把等待也算进去了）。**没有固定换算率 ⇒ 每行 ms 不能直接当墙钟读。**
- **还能用**：**同一张表内部的比较**。跨档比值（dense 每行腰斩）、同档内的相位排名
  （专家读是每行最大单项）、以及「谁随 T 涨谁不涨」这类结论 —— 都不受换算率影响。
- **仍然独立成立**：HC 相位对字节减半无感（另有 `STRATA_HC_Q8=1` 的 −7.4% 佐证）。

⇒ 「专家读 742 GB/s ≈ 峰值 82%」这类**由绝对 ms 换算出来的数**，在拿到权威的墙钟/DRAM 数据之前**不能用**。
它既可能是健康的，也可能不是 —— 目前**没有**证据支持任何一边。

## 5. 三种比法，只有一种站得住

| 比法 | 结果 | 可用性 |
|---|---|---|
| 相位**和**斜率 3.09 vs 剖析器关的墙钟斜率 4.50* | 差 1.4 ms/行 | ❌ 单位不同，且换算率随 T 变（1.59 → 1.09） |
| 剖析器开 7.97+4.83T vs 剖析器关 7.16+4.50T | 差 0.81 固定 + 0.33 ms/行 | ✅ 同单位 —— 但这是**剖析器自身的代价**（打点开销 + 关掉 fork） |
| 剖析器开的墙钟斜率 4.83 vs 相位斜率 3.09 | 差 1.74 ms/行 | ⚠️ 分母是「相加」口径，没有换算率 |

\* 剖析器关的干净拟合取自本轮引擎直报：T=1.00 → 11.66 ms/窗、1.00 token/窗；
T=3.98 → 25.08 ms/窗、2.70 token/窗 ⇒ **7.16 + 4.50×T**。
（2-2c 记的是 6.98+4.68T：②-2d 的 Q8_0 交错让**每行便宜 3.8%**，与端到端「T 越大越赚」吻合。）
引擎**直接报 token/窗**，不用反推接受率：T=3.98 时 2.70 token ⇒ 三个草稿位平均接受率 0.567，
而加一个草稿行的收支平衡点是 4.50/9.29 = **0.484** ⇒ 第四个草稿行仍微赚。

## 6. 一个工具坑（本轮浪费了 20 分钟）

`w22c_fit.py` 里的相位数字是**手抄硬编码**的（`phases = {'VRAM hits': (1.16+1.13+...), ...}`），
它从不解析日志。所以第一次「重跑拟合」看到一模一样的输出时，我误以为补丁没生效。
**⇒ 复用别人的拟合脚本前先看它是不是真的在解析。** 后来改成带日志偏移（`wc -l` 前后）只切本次的行。

## 7. 下一步：别再用相位表称绝对重量

要回答「专家读到底是不是 82% 峰值」，需要的是**权威的墙钟 + DRAM 字节**，而不是任何差值推导：

1. **nsys 抓单个验证窗**（推荐）：逐内核墙钟 + DRAM 吞吐/字节，一次拿到每个相位的真实占比和
   专家读的真实带宽。抓 ~30 个窗口即可，不需要改代码。
2. 或者把剖面的时间戳改成**墙钟口径**（每个 stage 只打自己 span 的首尾，不做逐层相加）
   —— 但要动的东西比 nsys 多。

在此之前：**候选①（专家读）保持挂起，不关闭也不启动。**
已经确定的几件事不变：① GpuPlanSink 已按 distinct expert 去重，**「跨窗重复读」这条命题不成立**；
② 草稿深度已在收支平衡点附近（0.567 vs 0.484）；③ HC 量化判死；④ `fuse_*` 三个融合在 CUDA 上不存在。
