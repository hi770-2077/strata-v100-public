# HC 投影 Q8_0 化：一个「字节减半」假设的完整证伪（2026-10-15）

> **假设**：decode 每 token 每层要读 1.26 GiB 的 BF16 超连接（hyper-connection）投影，
> 压成 Q8_0（0.67 GiB）应该拿到接近 +10% 的 decode 吞吐。
> **结论：−7.4%（111.0 vs 119.9 tok/s），flag 保持关闭。**
> 本文记录完整过程——包括一个先装成「内核 bug」的主机侧解码错误，
> 以及为什么「字节减半」在这个位置买不到任何东西。

---

## 1. 假设从哪来

IQ3_S 包里每条超连接投影（`output_hc_down/up` 与每层 `blk.*`）都是 BF16（ggml type 30），
生产 decode 路径（`fused_gr_read`，单 token）和 verify 路径（`fused_gr_read_multi`）
每个 token 每层都要全读一遍：合计 1.26 GiB（inject 行保留 BF16，实际量化部分 1.19 GiB）。
Q8_0 布局（34 字节 = 2B fp16 scale + 32×int8）是引擎 F32 分支已经在产的格式，
kernels 无需改动——只需要主机侧把 BF16 量化一遍上传，读取量降到 0.67 GiB。
按「decode 是带宽瓶颈」的常识，这应该值 +10% 左右。

## 2. 第一轮：一个装成内核 bug 的主机侧错误

开 flag 第一次跑：non-finite、0 token、content:null。用 `STRATA_HC_Q8_NOREAD=1`
（Q8 副本照常上传、读取仍走 BF16）隔离：输出正常 ⇒ 疑点指向 q8 读取内核。

写了独立的 parity bench（自持 fork 内 `src/kernels/hcq8_parity.cpp`）：复刻引擎精确调用形态
（q8_inject=null、xn scratch、图捕获重放），并带**主机侧 Q8_0 真值**（同字节反量化 +
双精度累加）——GPU 结果对真值只应差舍入，对 BF16 的差才是量化距离。

真因不在内核：主机量化器的 `bf16_to_f32` 按 **FP16 的 bias-15** 解码指数
（`exp - 15 + 127`），而 BF16 与 F32 一样是 **bias-127**。后果链：

```
权重 ~0.5  →  解码成 ~1e33  →  块内 amax ~1e31  →  fp16 scale 溢出成 +Inf  →  Q8 读回 Inf/NaN
```

正确实现就是 payload 左移 16 位——与 GPU 内核 `unpack8` 的
`__uint_as_float(w << 16)` 逐位一致。修复后引擎冒烟立即正常
（36 token / finish=stop / 82.6 tok/s）。

**两个把自己坑了的坑（教训比结论值钱）**：

1. bench 的权重生成器一开始是 FP16 转换器的字节级复制品，生成的「BF16 权重」
   主机解码 ~1e33、GPU 解码 ~1e-12，先「找到」一个假 NaN，差点误导成内核 bug。
   **bench 的权重生成器必须与内核解码约定逐位对齐。**
2. bench 的 `rel_err` 写成 `|got - |ref|| / |ref|`（减了绝对值而不是参考值），
   负参考值精确相等也报 rel 2.0，一度让人以为三个输出全错。
   **观测函数先自检。**

## 3. 修复后的验证：功能完全成立

V100 实测（`STRATA_SM70_TABLE=1`）：

| 检查 | 结果 |
|---|---|
| hcq8_parity（T=1..8，含/不含 pending write、最终 mixer、单 token 入口、图捕获重放） | **22/22 通过**。rs 逐位（单 token 入口 1e-7 为求和序差）、inject_out abs≤5.7e-6（序差）、R_out/xn 图像逐位、mixed 对主机真值 abs≤3.6e-7 / rel≤1.3e-3（相对误差仅出现在抵消主导的近零元素） |
| 质量门禁（8 条固定 prompt，temp 0，seed 1234） | 与 BF16 基线**逐字相同 8/8** |
| 冒烟 | 36 token / stop / 82.6 tok/s，无 non-finite |

也就是说：量化本身是干净的，输出质量无损。**不错与快是两回事**——下一步才见分晓。

## 4. 速度：假设被证伪，−7.4%

同一二进制只切环境变量，ABABAB 交替 3 visits × 2 rounds，每轮 prompt 加 salt
防服务端前缀缓存命中（读数用引擎自报 timings，best-of-N）：

| 臂 | decode |
|---|---|
| BF16（生产路径） | **119.9 tok/s** |
| Q8_0（`STRATA_HC_Q8=1`） | **111.0 tok/s（−7.4%）** |

机制（与窗口③-2 的结论互相印证，见 [`window3-2-hc-production-kernels-2026-10-15.md`](window3-2-hc-production-kernels-2026-10-15.md)）：

1. **decode 根本不被 HC 投影的 DRAM 流量约束**——MoE 专家主导每步读取，
   HC 读取只占解码 GPU 时间的一小块，字节减半省不下什么；
2. q8 内核用全局 partials 的算法，**单次读取比生产 staged BF16 读更慢**，
   字节减半的收益被算法低效吃掉还倒贴。

窗口③-2 已实测「HC 读内核微优化」六个候选全阴；本轮证明「量化减字节」同样是负的。
**这条路上两个方向结论一致：HC 读取不是 decode 的瓶颈，别再往这投。**
