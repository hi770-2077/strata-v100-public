## 1. 方法

与窗口 ③-1 完全同协议（可跨档对比），跑了两遍：

- **第一遍（剖析器开）**：`STRATA_VERIFY_PROFILE=1` + `STRATA_DECODE_TIMING=1`（后者是前者的打印门控），
  拿逐相位账单。⚠️ 剖析器会关掉 shared-expert 分支和 df_branch 且自带计时开销，
  **绝对值不可信，只有两个 T 之间的差可用**；两 stage 相加是双卡并行，与墙钟差一个并行因子——与 ③-1 同口径，跨档对比成立。
- **第二遍（剖析器关，只留 DECODE_TIMING）**：拿干净墙钟拟合——IQ3_S 的参照账 7.79 + 4.49×T 就是剖析器关着测的，
  跨档比必须同口径。

两遍都按请求 `spec_min_p` 零重启扫 T（1.0 → T=1，0.0 → T=4），中英两条叙述性 prompt 各 3 轮。

**引擎自报拟合（ms/窗 = a + b×T）：**

| 口径 | Q4_K_M 档 | IQ3_S 档（窗口 ③-0） | 差 |
|---|---|---|---|
| **墙钟（剖析器关）** | **6.98 + 4.68×T**（残差 ≤0.07） | 7.79 + 4.49×T | 固定 **−10.4%**，每行 **+4.2%** |
| 剖析器开 | 7.76 + 4.99×T（残差 ≤0.16） | —（仅用于相位差） | — |

原始账单（剖析器关）：T=1.00 → 11.66 ms/窗（三轮分毫不差）；T≈3.96 → 25.51 ms/窗。
**固定成本降了一成、每行只涨 4%**——每行那 +0.19 ms 与共享专家字节 +48% 的折算（≈+0.17 ms）几乎严丝合缝（§4）。

**三个结构性发现：**

1. **dense 每行成本腰斩，②-2b 的预言成真。** 隔离基准说 Q8_0 多列共享权重读取得当
   （nc=4 只比 nc=1 多 41%，字节没多读）；生产账本证实：验证窗从 1 行到 4 行，
   dense 的边际成本 0.41 → 0.18 ms/行。**「把带宽从 37% 往上做」在这个档确实没病可治——
   多列摊薄已经自动发生了。** 窗口 ② 关闭的判决维持。
2. **超连接相位对字节减半完全无感。** HC 投影从 BF16 变 Q8_0（同形状，2 B/元素 → 1.06 B/元素，
   字节近半），hc down/up 的每行成本**纹丝不动**（0.35→0.31 / 0.21→0.21）。
   这解释了 `STRATA_HC_Q8=1` 为什么实测 −7.4%：**HC 相位不是带宽受限，量化它的字节省不了时间**——
   两档、两个独立实验（运行时开关 + 换档）指向同一结论。别再碰 HC 量化。
3. **lm_head 变贵了。** head 相位每行 +0.14、T=1 固定成本翻倍（0.95→2.02，两 stage 相加）。
   lm_head 从 Q6_K 变 Q8_0：644 MiB 每窗至少整读一遍，词表 248 320 的账在 Q4_K_M 档更贵。
   这是换档的**隐性代价**，之前没入账。

## 3. 固定成本（T=1）里谁最大

两 stage 相加、T=1 列：**VRAM hits 3.06 > head 2.02 > hc down 1.76 > hc up 1.69 > dense gemv 1.67 > shared+quant 1.65**。
和 IQ3_S 档同构：**专家读 + 超连接 + lm_head 是固定三巨头**，dense 投影退居第四。
生产工作点（min_p 0.8，T≈2.2，干净账 6.98 + 4.68×T）：每行项占 4.68×2.2/17.3 ≈ **60%**，
其中专家读 1.34×2.2 ≈ 2.95 ms ≈ 全窗口的 17%。

## 4. 每行 +4% 的账：共享专家

剖析器每行 3.09（两档相同），墙钟每行 4.49→4.68。差值（剖析器关掉的 shared-expert 分支 + df_branch）
从 ~1.40 涨到 ~1.90 ms/行。**对账**：共享专家在 Q4_K_M 档也变 Q8_0——
gate/up/down 从 0.88+0.83+1.66 变 1.66×3 = 4.98 MiB/层（**每行字节 +48%**），
按 ~450 GB/s 折算 **+0.17 ms/行**，与墙钟每行的实测涨幅 **+0.19 ms** 几乎严丝合缝。
**共享专家是每行必读的常驻权重，它是这次换档唯一的每行净增成本**——dense 腰斩省下的、
lm_head 变贵花掉的，都在剖析器账本里；墙钟层面真正变贵的只有共享专家这一项（+48% 字节）。

**工作点核对**：生产 min_p 0.8 下 T≈2.2 → 6.98 + 4.68×2.2 = 17.3 ms/窗，
按接受率折后 token/窗 ≈1.96 → **≈113 tok/s**，与生产实测（110–123，口径不同）吻合，账本自洽。

## 5. 下一步候选（按这份账重排）

1. **专家 VRAM 读（1.34 ms/行，连续两档头号）**：每行读自己的 top-10 专家、行间不共享。
   可行方向是**跨行共享专家交集**（T 行的 top-10 有重叠时合并读取）——这是调度/内核联合手术，不是量化能解的。
2. **lm_head（+0.24/行 + 固定翻倍）**：Q8_0 的 644 MiB 每窗整读。候选是**词表切分/延迟 lm_head**
   （投机解码下只有被拒位置需要全词表 logits？）——需要先读引擎源码确认现有做法。
3. **HC 量化路线正式判死**（两档独立证据，见 §2 发现 2）。
4. 剖析器外那 ~1.90 ms/行已在 §4 对账（主体 = 共享专家字节 +48%）。剩余未拆名部分（df_branch 侧 ~0.3 ms/行）
   要更细的手段才能点名，优先级放后。
