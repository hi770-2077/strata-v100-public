# 窗口 ②-2：dense 投影的实测带宽账（2026-10-15）

> 承接窗口 ③-0：`ms/窗 = 7.79 + 4.49×T`，其中"固定 7.79 ms"被假定为 dense 权重读（估 3.2 GB ÷ 411 GB/s）。
> 本轮把这笔钱**实测**出来，而不是估。
> **结论：dense 是 2.26 GiB / 前向，T=2 时 5.54 ms，占生产窗口 31%（不是 44%）。**
> 而且 dense **不是固定的**：同样 2.26 GiB，1 列 4.53 ms，4 列 7.47 ms —— 多列内核把DRAM 打到只有 25–32%。

---

## 1. 方法

新增 `src/kernels/win22_dense_bench.cpp`，直接链到**生产构建树自己的静态库**
（`strata-1771/build-cuda/libstrata_kernels.a`，即 `/home/shun/tmpwork/strata-1771/build-cuda/strata` 的同一份目标码），
跑 GGUF 里读出来的真实 dense 形状与量化类型，逐形状 × 逐列数计时，同时量 IL（交错激活）内核的 rows1/2/4。

形状取自 GGUF `blk.0`，并对照 `native_dense.cpp` 的 `eligible()` 白名单（只有这 6 个张量走 `native_mmvq`）：

| 类型 | n_in → n_out | 张量 | MiB/层 |
|---|---|---|---|
| Q6_K | 2560 → 10240 | `attn_qkv` | 20.51 |
| Q8_0 | 6144 → 2560 | `ssm_out` | 15.94 |
| Q4_K | 2560 → 6144 | `attn_gate` | 8.44 |
| Q8_0 | 640 → 2560 | `ffn_down_shexp` | 1.66 |
| Q4_K | 2560 → 640 | `ffn_gate_shexp` | 0.88 |
| IQ4_XS | 2560 → 640 | `ffn_up_shexp` | 0.83 |

合计 **48.25 MiB/层 × 48 层 = 2.26 GiB / 前向**（与 T 无关，权重只读一遍）。

> 注：hc_attn_*/hc_ffn_*（BF16，12.5 MiB/层 ≈ 0.60 GiB）不在 `eligible()` 里，走的是另一条 bf16 GEMV 路径，本轮没量。

运行必须带 `STRATA_SM70_TABLE=1`（生产同款）：否则 `il_arch_ok()` 为假，IL 一栏会退化成 `native_mmvq`。

## 2. 实测（V100-PCIe，两遍一致到 ±0.02 ms）

`multi` = `native_mmvq`（非 IL 类型走这条）；`il r*` = `native_mmvq_il` 指定 rows/warp。

| | | | 3 | 58.3 | 51.7 | **43.0** | 49.8 |
| | | | 4 | 67.9 | 54.4 | 51.8 | **50.9** |

| | | | 2/3/4 | **28.5 / 30.0 / 31.9** | – | – | – |

| | ncols=1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 只用 multi | 4.53 ms | 5.80 | 6.53 | 7.47 |

单卡读带宽实测峰值 859 GB/s ⇒ dense 只跑到峰值的 **62%（1 列）→ 49%（2 列）→ 38%（4 列）**。

### 2.1 单列已经接近最优，问题全在多列

ncols=1 的每类型有效带宽：**Q8_0 693 GB/s（81% 峰值）、Q6_K 574（67%）、Q4_K 487（57%）**。
同一份 2.26 GiB，4 列要多花 **2.94 ms（+65%）**，字节一个都没多读。

## 3. ncu：为什么多列慢

（ncu 时长比 bench 高 ~18%，看比例不看绝对值）

| 内核 | 时长 | DRAM 利用率 | SM 吞吐 | 寄存器/线程 | 理论占用率 | 发射指令数 |
|---|---|---|---|---|---|---|
| Q6_K nc=1 `q6_k_mmvq<0>` | 42.7 µs | **62%** | 63% | 40 | **75%** | 9.94 M |
| Q6_K nc=4 `multi<…,4,4,2>` | 81.2 µs | **32%** | 54% | **80** | **37.5%** | 16.65 M |
| Q4_K nc=4 `multi<…>` | 46.8 µs | **25%** | 41% | **80** | **37.5%** | 7.31 M |
| Q8_0 nc=1 `small_mmvq<Q80Block,8>` | 28.7 µs | **81%** | 27% | 39 | 75% | 2.58 M |
| Q6_K nc=4 `il_kernel<IlQ6K,4,1>` | 63.2 µs | 38% | 46% | **80** | **37.5%** | **10.69 M** |

- **诊断一：多列内核不是 DRAM 受限，是指令发射受限 + 占用率腰斩。**
  同样 128 线程/CTA，nc=1 用 40 寄存器 → 12 blocks/SM（75% 理论占用）；
  nc=4 用 **80 寄存器 → 6 blocks/SM（37.5%）**。nc=4 每 warp 的发射间隔反而更短（9.56 vs 15.67 周期，ILP 更好），
  但可用 warp 数减半 ⇒ 净吞吐更低。DRAM 有 **68–75% 的时间在空转**。
- **诊断二：IL 赢在指令数，不赢在占用率。**
  IL rows1 与 multi 同为 80 寄存器 / 37.5% 占用，但**指令数少 36%**（10.69 M vs 16.65 M）⇒ 快 22%。
  交错布局让一次 16 B 载入取到所有列的同一位置。
- nc=1 的主导 stall 是 **Long Scoreboard（等 L1TEX 数据）6.2 周期 / 15.7 周期的 39.6%** —— 延迟受限，靠占用率掩盖。

⇒ **两个可叠加的抓手：把 80 寄存器压到 ≤40（占用率 37.5% → 75%），以及继续压指令数。**

### 3.1 抓手一已试过，是死路：`__launch_bounds__` 抬 minBlocks ⇒ 寄存器溢出

`native_mmvq_multi_kernel` 的 `__launch_bounds__(NW*WARP, ROWS<=2?4:1)` 把下限抬到 **12**（⇒ ≤40 寄存器），
IL 内核同步加上同样的下限。parity **逐位通过**（`mmvq_multi_parity` 148480 输出 0 差异；`mmvq_il_parity` OK），但速度崩了：

| | 基线 nc=2 | MINB=12 nc=2 | 基线 nc=3 | MINB=12 nc=3 | 基线 nc=4 (IL r4) | MINB=12 nc=4 |
|---|---|---|---|---|---|---|
| attn_qkv Q6_K | 50.2 | **52.3** | 58.3 | **184.3** | 50.9 | **329.0** |
| attn_gate Q4_K | 25.4 | **29.4** | 29.3 | **37.6** | 25.3 | **215.6** |
| ssm_out Q8_0 | 28.5 | **31.9** | 30.0 | **45.3** | 31.9 | **71.8** |
| 合计 48 层 | 5.80 ms | **6.29 ms** | 6.55 ms | **13.79 ms** | 7.48 ms | **10.95 ms** |

**连 nc=2 都变慢 4–16%**，nc=3 慢 3 倍 ⇒ 这 80 个寄存器是内核真需要的，不是编译器浪费；
压到 40 只会 spill 到 local memory。已回滚（`strata-v100-opt` 源码 md5 与生产树重新一致，fork-build 已重建，
基线重测 4.532/5.796/6.550/7.481 ms 与首次一致）。
占用率只能靠**改内核结构**（例如把列分给不同 warp，让每线程只留一个累加器），不能靠编译指令白拿。

## 4. 顺手发现：sm_70 的 IL 表在我们这张卡上有两格选错

`kIlRows_70` 是 PR 1401 在 **V100-SXM2** 上读出来的；我们是 **V100-PCIe**。用我们自己的 bench 复核：

| 类型 | n_out 类别 | ncols | 表给的 rows | 实测最优 | 差 |
|---|---|---|---|---|---|
| Q6_K | 10240（cls 3） | 2 | 2 → 48.8 µs | **1 → 44.3 µs** | −4.5 µs/层 |
| Q4_K | 6144（cls 2） | 2 | 2 → 21.4 µs | **4 → 20.3 µs** | −1.1 µs/层 |
| Q6_K / Q4_K | 其余格子 | | | 与表一致 | 0 |

其余格子（含 n_out=640 的小形状判 IL 关闭）都对。**合计 −5.6 µs/层 × 48 = −0.27 ms/窗 ≈ +1.5%**，
而且 `STRATA_MMVQ_IL_ROWS` 可以不重新编译就改（IL 的输出与 `native_mmvq` 逐位相同）：

```
STRATA_MMVQ_IL_ROWS="14:2:0,2,2,1,2;12:2:0,2,4,2,2"
```

## 5. 预算重算（推翻 ③-0 的一处估算）

③-0 写"固定 7.79 ms ≈ dense 3.2 GB ÷ 411 GB/s"。实测 dense 只有 2.26 GiB，且随 T 涨：
`dense(T) ≈ 3.98 + 0.55×T` ms（引擎实际，IL 生效）。代入 `ms/窗 = 7.79 + 4.49 T`（T=2.22 时 17.76 ms）：

| 组成 | ms/窗 | 占比 |
|---|---|---|
| dense 投影（实测） | 5.5 | **31%** |
| MoE 专家读（估，0.95 GB/行 ÷ 450 GB/s） | 4.7 | 26% |
| 每行"其他"（注意力+GDN+indexer+combine+head） | 4.2 | **24%** |
| 固定"其他"（HC bf16 + 空隙 + MTP …） | 3.8 | **21%** |

**⇒ dense 不再是最大单项；两个"其他"合计 45% 才是，而且仍然没有名字。**
窗口 ② 的天花板也随之下降：即使 dense 全部做到 nc=1 的速率（4.53 ms 恒定），
也只省 1.0 ms（T=2.22）⇒ **+6%**；若把最优点一起推上去（T→2.7）约 **+8%**。

## 6. 结论与下一步

1. **窗口 ② 的天花板实测为 +6~8%**，不是路线图里写的 +10~15%。要继续做，抓手只有两个（可叠加）：
   - **寄存器 80 → ≤40**：`native_mmvq_multi_kernel` / `native_mmvq_il_kernel` 的
     `__launch_bounds__(NW*WARP, ROWS<=2?4:1)` 把下限从 4 blocks/SM 抬到 12，编译器就得把寄存器压下来。
     一行改动，语义不变（除非溢出到 local memory，需要 parity 校验）。
   - **指令数**：IL 已经赢 36%，继续走交错/更宽载入的方向。
2. **免费的 +1.5%**：`STRATA_MMVQ_IL_ROWS` 修上面两格（已验证逐位相同）。
3. **优先级建议上调"其他"45% 的命名工作** —— 用 `STRATA_VERIFY_PROFILE=1` 在两个 T 下各取一份相位报告相减，
   把"每行 4.2 ms / 固定 3.8 ms"点名。它现在是最大的一块，而且完全没被看过。
