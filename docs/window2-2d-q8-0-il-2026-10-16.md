# 窗口 ②-2d：把 Q8_0 接回交错 MMVQ，以及共享专家那条对账的否证（2026-10-16）

> 承接 [`window2-2c-window-account-q4k-2026-10-16.md`](window2-2c-window-account-q4k-2026-10-16.md) §5 重排的两个候选。
> **结论一（采纳）**：Q8_0 在 `native_mmvq_il` 里从来没被放行过——换到 Q4_K_M 档后，
> **全部 dense 投影 + 超连接混合器 + lm_head 都是 Q8_0**，于是它们集体吃了没交错的那条慢路径。
> 补上内核/派发/sm_70 表后逐位一致，**生产默认工作点 +0.8~1.2%，T=4 时 +1.6~2.1%**，已上生产。
> **结论二（否证）**：候选①「专家读的跨行共享」是**已经做过的**事，不是没做；
> 而且 2-2c §4 把「每行 +0.19 ms」归给共享专家字节 +48% 的那笔账**被源码否证**——
> 共享专家是 `shared_expert_multi(n_tok)` 按窗口批量算的，**与 T 无关**，不该出现在每行斜率里。
> ⇒ 那 ~1.9 ms/行（≈全窗口 24%）重新变成**未点名**的最大单项，升为头号候选。

---

## 1. 起因：Q8_0 从来没进过交错的门

`native_mmvq_il` 的允许类型只有 23/12/13/14/11（IQ4_XS / Q4_K / Q5_K / Q6_K / Q3_K）。
**Q8_0（type 8）不在里面**——它在 IQ3_S 时代只出现在个别边角，没人管。

换档之后这件事的性质变了：Q4_K_M 档里

- 每层全部 dense 投影（attn_qkv / attn_gate / o_proj / router）、
- 超连接 mixer 的 down/up、
- **lm_head（2560×248320，644 MiB）**

**全是 Q8_0**。也就是说换档之后，引擎里最大、最热的那批 GEMV 全都被挡在交错路径外面，
走的是 `native_mmvq` 的普通多列内核。单列（T=1）更彻底：sm_70 的 `kIl1Rows_*` 表根本没有 Q8_0 条目。

隔离基准（V100-PCIE，本档真实形状，`mmvq_il_parity --bench`）：

| 形状 | 列数 | `native_mmvq` | 交错（最优行宽） | 变化 |
|---|---|---|---|---|
| head 2560×248320 | T=1 | 860.9 µs | **825.0** | −4.2% |
| head 2560×248320 | T=2 | 1009.8 | **851.4** | −15.7% |
| head 2560×248320 | T=4 | 1202.3 | **927.4** | −22.9% |
| 2560×10240 | T=2 | 46.9 | **40.8** | −13.0% |
| 2560×640 | T=1 | 5.9 | 7.8 | **+32%（输）** |
| 640×2560 | T=1 | 6.0 | 5.6 | −6.7% |

注意 2560×640 那行：**小形状上交错是输的**。所以不能无脑全开，必须按 (类型, 列数, n_out 档) 逐格决定——
这正是行宽表存在的意义。

## 2. 做了什么

`src/kernels/cuda/native_mmvq.cu`：

1. `struct IlQ80`：Q8_0 块 32 元素 / 34 字节，走 `SmallTraits<Q80Block, 8>`，
   两段 dp4a（`r.v[0]` / `r.v[1]`）打 `x.u(kby, iqs)` 与 `x.u(kby, iqs+1)`，与单列点积逐位一致。
2. `native_mmvq_il_supported` 放行 `ggml_type == 8`；派发 switch 加 `case 8`。
3. `validate_shape(n_in, ncols, QK)` → 对 Q8_0 用 `Q8K`（Q8_0 块是 32 元素，用 QK=256 会把 640 输入的形状直接拒掉）。
4. sm_70 表 `kIlRows_70` 加 Q8_0 三行、`kIl1Rows_70` 加 `{8, {0,0,0,0,1}}`（只有 head 那一档赢，小形状留给原内核）。

表是这个卡实测出来的（`--bench --emit-table`，三个 n_out 档 × 列数 2/3/4）：

```
{8, {{0, 1, 4, 2, 2}, {0, 1, 1, 4, 4}, {0, 2, 2, 4, 2}}}
```

⚠️ **`kIlRows_70` 原本是从 V100-SXM2 读的，Q8_0 这三行来自 V100-PCIE。** 同一张卡的实测表，但卡型与前几行不同源——
后面谁要在这张表上再动刀，记得先对齐口径。

## 4. 端到端 A/B（隔离赢 ≠ 端到端赢，铁律一）

四轮，同一二进制只切环境变量，每条 prompt 逐位可复现（**不加 nonce**）：

| 轮次 | 设计 | min_p=1.0（T=1 窗） | min_p=0.0（T=4 窗） |
|---|---|---|---|
| 1（A→B→C 正序） | 三臂 | +0.23% / +0.11% | **+1.60% / +1.88%** |
| 2（**C→A 反序**） | 两臂，抵消漂移 | +0.35% / +0.23% | **+2.10% / +2.10%** |

反序那一轮是关键：C 先跑、A 后跑，C 依然全胜 ⇒ **不是「机器越跑越快」的漂移**。
（轮次 3 用 UUID nonce 跑过一次，方差 ±8%，**作废**——nonce 改变了生成内容、T 分布随之改变，
对 1% 量级的效应是废数据。想配对就必须确定性。）

生产默认工作点（引擎默认 min_p，T≈2.2，4 轮 × 3 prompt，确定性）：

| prompt | 基线（旧派发） | 采纳后 | Δ |
|---|---|---|---|
| 中文-投机解码 | 108.30 | 109.60 | **+1.20%** |
| 英文-投机解码 | 111.80 | 113.10 | **+1.16%** |
| 中文-V100 | 114.20 | 115.50 | **+1.14%** |

（A/B 当时量到 +0.70~0.83%，上生产后复测 +1.14~1.20%，取 **+0.8~1.2%** 这个区间报。）
**T 越大越赚**（T=1 +0.2% → T=2.2 +1% → T=4 +2%），与「交错的本質是多列共享权重读取」完全自洽。

**同时记录一次「隔离基准高估」**：head 在 T=4 隔离快 22.9%，端到端只有 +2%。
因为 head 只占窗口的一部分，且窗口里还有几十个内核在混跑。**这是本仓库第四条同类证据**
（前三条见 `window2-2b-dense-q4k-2026-10-16.md`），铁律一继续保持。

## 5. 候选①：不是没做，是早就做了

2-2c 把「专家读的跨行共享」排在第一，理由是「每行读自己的 top-10 专家、行间不共享」。
读源码的结论是**这个共享已经存在**：

- `resident_plan_kernel` / `expert_source.cpp` 建 GpuPlanSink 时**按 distinct expert 分组**
  （按路由顺序去重，每个专家的 dst/token 只列一次），所以**窗内不会重复载同一份专家权重**；
- 组内复用在 `GRP_NC` 批次里（`native_gu_multi_kernel`）。

实测也支持「这里没病」：每行专家流 995 MB/窗，1.34 ms/行 ⇒ **742 GB/s ≈ 峰值 900 的 82%**。
这是健康值，不是 37% 那种病灶。
**每行比 IQ3_S 档贵 +12% 是因为 Q4_K_M 档的专家本身更大（IQ2_S/IQ4_NL），不是共享没做。**
⇒ 候选①关闭，别再往这上面花时间。

## 6. 顺手否证：2-2c §4 那笔「共享专家」的账站不住

2-2c §4 说：墙钟每行从 4.49 涨到 4.68（+0.19），而共享专家字节 +48%（3.37 → 4.98 MiB/层），
按 450 GB/s 折 +0.17 ms——「几乎严丝合缝」，于是把每行净增判给共享专家。

**源码说这不成立**：`verify.cpp:1567` 调的是 `shared_expert_multi(n, ...)`，`n` 是整个窗口的 token 数，
里面 `native_mmvq(..., n_tok)` **一次批量算完**——**共享专家的权重读取与 T 无关**。
一个 T 无关的量，不会出现在「每行斜率」里。

隔离基准直接印证（Q8_0 2560×640，正是共享专家 gate 的形状）：
**T=1 5.9 µs → T=4 7.9 µs**，4 倍 token 只多 2 µs——主体是权重读取，且几乎不随 T 变。
按这个数估，共享专家 48 层 × 3 个投影 ≈ **0.9~1.2 ms/窗**，属于**固定成本 6.98 里的一块**，
不是那 ~1.9 ms/行。

⇒ **那 ~1.9 ms/行（≈4.2 ms/窗、全窗口 24%）的解释权重新开放，且它是目前最大的单项。**
`STRATA_DF_BRANCH` 默认关、剖析器也关它，所以另一半 `df_branch` 同样贡献不了这个斜率。

## 7. 下一候选（按本轮重排）

1. **（新头号）把剖析器外那 ~1.9 ms/行点名。** 它是全账最大单项（≈24% 窗口），
   而上一个解释（共享专家）刚被源码否证。手段：给这两条分支单独打点，或用 nsys 抓单个验证窗。
   **在点名之前，任何针对它的优化都是猜。**
2. **专家 VRAM 读（1.34 ms/行，742 GB/s = 82% 峰值）**：只剩 ~18% 到顶，
   理论上限约 0.24 ms/行 ⇒ 全窗口 ~3%。可做但天花板低。
3. **lm_head**：本轮已吃到（隔离 T=4 −22.9%、端到端 +1~2%）。剩下的是 644 MiB/窗的硬读取，
   实测已 780 GB/s 档，**没剩什么**；投机解码下每个被验位置都需要全词表分布，切词表也没有正确性空间。
4. **HC 量化路线判死**（两档独立证据，见 2-2c §2 发现 2 与 `hc-q8-2026-10-15.md`）。
