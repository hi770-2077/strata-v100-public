# 窗口 ②-2b：换到 Q4_K_M 档之后，dense 这条路又量了一遍（2026-10-16）

> 承接 [`window2-2-dense-mmvq-2026-10-15.md`](window2-2-dense-mmvq-2026-10-15.md)。
> 那一篇是在 **IQ3_S 档**上做的：dense 投影是 Q6_K / Q4_K / IQ4_XS / BF16 的混合体，2.26 GiB / 前向。
> 2026-10-16 生产模型换到 **Q4_K_M 档**，dense 的形状全变了：**每一层投影、超连接混合器、lm_head 现在都是 Q8_0**，
> 5.78 GiB / 前向（2.56×）。上一篇的结论不能直接搬，必须重测。
>
> **一句话结论：三个候选全部证伪。其中一个是「隔离基准快 8.5%、逐位相同、端到端慢 5%」——
> 这是本仓库「隔离基准会系统性高估」这条铁律迄今最干净的一个证据。**

## 1. 新的 dense 账本

新增 `src/kernels/win22b_acq4_bench.cpp`，形状直接从 Q4_K_M GGUF 的 `blk.0/blk.1` 读出来，
链的是**生产构建树自己的静态库**（`build-144/libstrata_kernels.a`，即服务正在跑的 0.1.44.1 目标码）。
13 个形状、逐列数计时，同时把每个 (形状, 列数) 的输出落盘做逐位比对。

| | nc=1 | nc=2 | nc=3 | nc=4 |
|---|---|---|---|---|
| ms / 前向 | **9.963** | 12.053 | 12.824 | 14.083 |
| 有效带宽 | 622 GB/s | 515 | 484 | 440 |

两个和 IQ3_S 档不一样的地方，值得单独说：

1. **Q8_0 单列已经很快**：695–785 GB/s，是实测峰值 859 GB/s 的 **81–91%**。
   IQ3_S 档那个「37% 带宽利用率」的病理在 Q8_0 上**基本不存在**——反量化越简单，内核越接近纯流式。
   窗口 ② 原本设想的「把带宽从 37% 往上做」这个抓手，在 Q4_K_M 档上**没有对应的病灶**。
2. **多列仍然塌**，而且小形状塌得更狠（hc_* 与 ffn_*_shexp 只有 209–390 GB/s）。
   同一份 5.78 GiB，nc=4 比 nc=1 多花 **4.12 ms（+41%）**，字节一个都没多读。

> ⚠️ **口径提醒**：上表是**整机 48 层**的 dense 读取量。生产是 `--layer-split 25`，
> 每卡只跑 25/23 层，所以单卡 dense ≈ 这个数的一半。
> 本文**不**据此断言 dense 占生产窗口的百分比——那要用引擎自报的逐窗账重新点名
> （IQ3_S 档的 31% 那张账在换档后已经作废，见 §5）。

## 2. 候选一：`STRATA_Q8_PACKED=1`（打包 Q8_0 布局）——逐位相同，但慢 40%

上游为其它架构准备的**无损重排**：把 Q8_0 的 32 个数据字节和 2 个 scale 字节拆成两个平面（qs 平面 + d 平面），
宣称逐位等价，在 Aurora 上是生产默认（`arch_defaults.cpp` 里标 +2.3%）。我们这张卡上：

| 张量 | nc | multi GB/s | packed GB/s | 逐位 |
|---|---|---|---|---|
| attn_qkv | 1 | 692 | **445** | MATCH |
| attn_gate | 1 | 642 | **444** | MATCH |
| ple_key | 4 | 511 | **399** | MATCH |
| output（lm_head） | 1 | 785 | **433** | MATCH |

**13 个形状 × 4 个列数全部 memcmp 逐位相同（diffs 0）**——上游的「无损」声明是真的。
但速度是**输的**，而且要看清口径才能诚实报数：packed 只接管 5 个「合格」形状
（`n_in ≤ 4096 && n_out ≥ 2048`，即 attn_qkv / attn_gate / ple_key / ple_value / lm_head），
所以 bench 打印的 `TOTAL packed` 不能直接和 13 形状的 multi 总量比。按生产真实行为
（合格形状走 packed、其余走 multi）合并：

| | nc=1 | nc=2 | nc=3 | nc=4 |
|---|---|---|---|---|
| 合格形状走 multi | 6.587 | 7.705 | 8.114 | 8.940 |
| 合格形状走 packed | **10.228** | 10.896 | 10.399 | 11.446 |
| 生产等效 dense 总量 | 13.617 | 15.277 | 15.138 | 16.630 |
| 基线（全 multi） | 9.976 | 12.086 | 12.853 | 14.124 |
| 差 | **+36.5%** | +26.4% | +17.8% | +17.7% |

单形状更直观：attn_qkv 单列 40.2 → **62.7 µs（+56%）**，lm_head 单列 860.8 → **1559.6 µs（+81%）**。

**为什么**（假设，未单独验证）：平面拆分把一个线程一次 34 字节的连续载入，换成两条互不相邻的流。
在大 L2 / 大扇区的卡上两条流各自都能完全合并；Volta 只有 6 MB L2、128 字节扇区，
两条流互相挤，实测有效带宽直接掉到 400 GB/s 档。**同一个 flag 两种卡两种结果**，
和 [`flag-ledger.md`](flag-ledger.md) 里 `STRATA_SPLIT_OWN` 那条是同一类教训。

## 3. 候选二：列分 warp 内核（`STRATA_MMVQ_COLWARP=1`）——寄存器假设对了，速度反而崩

窗口 ②-2 的诊断是：多列内核 80 寄存器 → 6 blocks/SM → 占用率 37.5%，DRAM 有 68–75% 时间在空转。
上一篇试过用 `__launch_bounds__` 硬压寄存器，结果是 spill 到 local memory，更慢（已记录）。
这次改成**改内核结构**：让每个 warp 只负责**一个输出列**，每线程只留一个累加器。

- **寄存器假设完全正确**：新内核 **38/48 寄存器、零 spill**（对比 multi 的 80 寄存器）。占用率确实上去了。
- **速度**：nc=4 **20.350 ms/前向** vs 基线 14.09 ms —— **慢 44%**。

**为什么**：列分 warp 之后，每个 warp 独立把自己那一列的**整块权重矩阵**从头读一遍。
nc=4 就是 4 份 DRAM 流量，而 V100 的 L2 只有 6 MB，attn_qkv 单块就 26.56 MB——
**L2 完全兜不住，省下的寄存器被翻倍的访存流量倒找回去还多付**。
占用率和访存局部性在这个内核里是直接对立的，不是可以同时要的两个好处。

⇒ 已整段从源码移除（`git diff src/kernels/cuda/native_mmvq.cu` 为空）。

## 4. 候选三：`STRATA_NO_MMVQ_ROWS2=1`——**本篇真正值钱的那一条**

上游 #783 PR-h 给 dense Q8_0 内核开了个每块两行的版本；`STRATA_NO_MMVQ_ROWS2=1` 强制退回每块一行
（每行自己的部分和、自己的归约，所以**逐位与两行版相同**）。gfx12 和 sm_86 上上游已实测更快，sm_70 没测过。

### 隔离基准：赢，而且逐位相同

| | nc=1 | nc=2 | nc=3 | nc=4 |
|---|---|---|---|---|
| 基线（两行） | 9.963 | 12.053 | 12.824 | 14.083 |
| ROWS2=1（一行） | 9.961 | **11.034** | 12.748 | **13.278** |
| 差 | ±0 | **−8.5%** | −0.6% | **−5.7%** |

逐形状看得更清楚（微秒，nc=2）：hc_attn_down 9.8 → **7.5**（−23%）、attn_qkv 47.0 → **43.4**（−7.7%）、
lm_head 1008.8 → **944.7**（−6.4%）。nc=3 处有回退（attn_qkv 49.3 → 50.6），但总量仍是赢的。

**52 个输出全部逐位相同**（纯 Python 逐字节比对，不是相对容差）。

### 端到端：输，慢 5%

同一二进制、只切 systemd dropin 里的环境变量，ABAB：

| | decode tok/s |
|---|---|
| 基线（重启前） | 106.75 / 108.4 |
| `STRATA_NO_MMVQ_ROWS2=1` | **101.35 / 103.45** |
| 基线（回滚后复测） | 109.5 / 108.3 |

回滚后**重跑了一遍基线**，确认环境变量真的清干净了（dropin 数量、进程 env、health 200 都核对过），
排掉「重启本身带来差异」这个解释。**净结果：隔离快 8.5%，端到端慢 5%，中间差了约 13 个百分点。**

### 为什么会这样（假设，明确标注未验证）

隔离基准是把同一个内核在独占的、已经热身的卡上背靠背跑 200 遍——DRAM 流水线完全摊开，
调度开销被后面紧接着的同一个内核吸收。生产里 dense GEMV 是和 MoE 专家计算、
层切分跨 PCIe 传输**并发抢同一张卡**的：

- 每块一行 ⇒ grid 从 `n_out/2` 变成 `n_out`，**块数翻倍**。独占时免费，混跑时是实打实的调度与尾部成本。
- 两行版每块吃两个输出行，天然更容易和邻居的访存重叠；一行版把并行度摊薄成更多的小块。

⇒ **这条不是「dense 内核没救」，而是「隔离基准不能单独作为判据」。**
本仓库窗口 ① 就立过这条铁律（隔离基准高估，端到端才是裁判），
但此前所有案例都涉及数值差异或幅度较小。**一个逐位相同、隔离快 8.5% 的内核端到端反而慢 5%，
是这条铁律最干净、最难反驳的证据**——它排除了「数值不同导致下游变慢」这一整类解释。

## 5. 关掉这条路，以及下一步

1. **窗口 ②（dense GEMV）在 Q4_K_M 档上暂时关闭。** 三个候选全灭，而且原本设想的病灶（37% 带宽）
   在 Q8_0 上不存在——单列已经 81–91% 峰值。剩下的多列塌陷（+41%）要的是**跨列共享权重读取**的结构性重写，
   不是调占用率或换布局能拿到的；按 §4 的教训，重写之前先想清楚怎么让它在混跑时也不亏。
2. **换档后必须重算的账**：IQ3_S 档那份「dense 31% / MoE 26% / 其他 45%」的逐窗分解
   （[`window3-1`](window3-1-naming-the-other-45pct-2026-10-15.md)）**已经作废**——dense 读取量从 2.26 GiB 涨到 5.78 GiB，
   占比几乎肯定变了。下一步最高价值的动作不是再写内核，而是**在 Q4_K_M 档上重取一份引擎自报的逐窗账**，
   重新点名各块。用 `STRATA_VERIFY_PROFILE=1` 在两个 T 下各取一份相位报告相减。
   **（当日完成：新账 ms/窗 = 6.98 + 4.68×T（剖析器关，IQ3_S 档为 7.79 + 4.49T），
   dense 每行腰斩、专家读仍是头号，见
   [`window2-2c-window-account-q4k-2026-10-16.md`](window2-2c-window-account-q4k-2026-10-16.md)。）**
3. **测量纪律加一条**（已写进 [`how-we-measure.md`](how-we-measure.md)）：
   隔离基准的胜负**只能用来筛掉明显更差的候选**，不能用来宣布收益；
   逐位相同也不能免检——它只保证单内核正确，不保证在并发环境下调度特性不变。

## 6. 复现

```bash
# 编译（链生产构建树自己的静态库 = 服务正在跑的目标码）
g++ -O3 -DNDEBUG -std=c++20 -DSTRATA_EXPERIMENTAL_SM60=1 -DSTRATA_VERSION='"0.1.44.1"' \
    -I/home/shun/strata-v100-opt/include \
    -isystem /opt/cuda-12.8/targets/x86_64-linux/include \
    -o win22b_acq4_bench src/kernels/win22b_acq4_bench.cpp \
    <build>/libstrata_kernels.a <build>/libstrata_core.a -lcudart -lcudadevrt -lrt -lpthread -ldl

# 三遍连跑（生产必须停服——单卡显存被引擎占满，bench 放不下）
sudo systemctl stop <service>
STRATA_SM70_TABLE=1 CUDA_VISIBLE_DEVICES=0 ./win22b_acq4_bench 200                      # 基线
STRATA_SM70_TABLE=1 CUDA_VISIBLE_DEVICES=0 STRATA_NO_MMVQ_ROWS2=1 ./win22b_acq4_bench 200
STRATA_SM70_TABLE=1 CUDA_VISIBLE_DEVICES=0 STRATA_Q8_PACKED=1     ./win22b_acq4_bench 200
sudo systemctl start <service>
```

`STRATA_WIN22_DUMP=<目录>` 会把每个 (形状, 列数) 的输出写成 `.bin`，供逐位/相对容差比对
（列分 warp 版只做到浮点舍入等价，`max_rel ≈ 1e-7`，所以不能用 memcmp）。
